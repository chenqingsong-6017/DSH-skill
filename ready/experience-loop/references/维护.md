## 维护 · 归并经验库（用户触发：「归并经验库」）

1. 读 `_索引.md` 和近 3 个月的 `复用回执/`。
2. 逐条处理：
   - **待修订（2.5.0 起分档）**：跑 `assets/回执统计.py` 看「待修订」两档输出——
     **定性**（`有 ✗·闸` ／ `连续 ≥2 次 △·闸`）⇒ **当场抄进 `经验库/_台账.md` 的待修订类**
     （每类 ≤10 行，「卡在讲什么」列强制）—— **这就是「判断的落点」**，不落＝判断悬空；
     **提示**（`·评` 的 ✗ ／ 连续 △）⇒ **只列出、不定性**——`·评` 是自评，拿它定性＝**自己批自己**。
     ⭐ **推翻型（3.5.1 加，人工识别、脚本不判）**：复用结果**推翻了卡上的「预期失效条件」≥2 次** ⇒ 同样属
     **定性**，抄进待修订类。它比 `✗·闸` 更早——`✗` 要等到任务整个失败，推翻只需一条边界对不上；
     **来源**：卡上的「预期有效／失效」字段（见 `assets/经验卡模板.md`）＋回执「新证据」列写 `有：E-0XX` 且备注标「推翻」。
     ⚠ 两档**都只采信单卡行**（多卡行会"共享"效果 ⇒ 假阳性）；本步**不用人工眼力**（2.4.0 起机械化）；
   - 长期零复用 → 从索引移除，内容压缩为一行并入 `经验库/_冷归档.md`；
   - 内容重叠 → 合并为一张，更新索引；
   - 复用 ≥3 且反馈好 → 升 **★核心**；若做法高度通用，**按下方「固化阈值」**提示用户可**升格**
     （**判阈前必须先跑「判阈前的输入体检」取可信次数，禁止凭印象数**）；
     若该做法**早已完整存在于某个载体里**（迭代 skill 时顺手吸收过）→ 那是**去重**，不走升格阈值。
3. **归并前的第一动作：读 `经验库/_台账.md` 的待修订类**（3.0.0 起三类台账合一）——它是「待修订」的**落点**，
   上次判出、本次还没处理的事项都在里面；处理完当行移除。
4. 输出归并报告：变更清单（合并／归档／★核心／待修订 各几条）
   ＋ ⭐ **机械证据覆盖率（2.5.0）**＝ `·闸` ÷ 已评（脚本直接打印）——
   它回答"**我们的奖励信号有多少踩在事实上**"；**`·闸` 为 0 或长期为 0 ⇒ 点名"无独立裁判"**
   ＋ **两本账（2.2.0 起分列）**——
   **方案闸账**（本季「过 1 轮／过 2 轮／直通／跳过」各几次）＋ **检索账**
   （`命中`／`未匹配`／`漏检`／`未涉及` 各几次，并算**命中率**）。**闸门值不值得、检索步有没有被跳过，
   就靠这两行判断**——旧版挤在一列，两件事互相污染，2026-10-03 起拆开。
   漏检 ≥2 次即在本报告里点名为「机制失效」，并复述 ② 段第 0 行硬闸。
   **检索账还要看分母**：`未涉及` 占比过半 ⇒ 先查是不是触发边界定得太松。保持索引精简本身就是省 Token。

> ⚠ **表格类载体（回执／台账／索引）加列、拆列、改列名——三个必踩的坑（2026-10-15 并入）**：
> ① **解析侧**：表头不能因正文打断而清空（回执中间夹引用块表格 ⇒ 后段成「无表头续写」被整块漏，
> 实测漏 12 行）；处理规则＝表头**只在遇到新表头时更新**，数据行按「列数＝表头列数 ＋ 日期列匹配」判。
> ② **写入侧**：旧行少新列会把**相邻列语义整体挤位**（备注被挤进「新证据」列）⇒ 迁移时给旧行补
> **占位符**（如 `—`）、消费脚本对占位符回退推断；**字符串替换改表格行同样会静默错位**（替换串少写
> 一个 `|` ⇒ 整行齐左、无任何报错）——改完**必须 `split("|")` 回读验字段数**。
> ③ **兼容侧**：「少一列」与「少两列」必须区别对待（容错写成"列数 ∈ {表头, 表头−1}"时，
> 少 2 列的历史行会把旧列值误读成新列语义）⇒ **严格等列**，不符则**跳过并计数、绝不猜**。
> 迁移判据＝**旧值有没有定义**（有定义 ⇒ 机械映射、零臆造、该迁；"历史没记" ≠ "不能迁"）。
> 收工三查：**行数与备份一致 ＋ 关键列逐行等值 ＋ 异常行 0**。

### 升格与下沉：双向通道（归并时最自然的决策点）

**判的是「命中率」，不是「重要程度」** —— 两边的成本模型是反的：

| | 长期记忆（`~/.workbuddy/MEMORY.md`） | 经验库 / skill |
|---|---|---|
| 何时载入 | **每次会话必进**（整份注入，永久占位） | 匹配到才载入 |
| 成本 | 内容量 × **会话数** | 只在用到时付一次 |
| 放错的代价 | 只跟某类任务有关的规则 → 在其余会话里是**纯噪音** | 每次都要遵守的规则 → 未加载时**漏执行** |

#### 升格与去重：先分清是哪一件（2026-09-27 重写）

**同一个闸门管不了两件成本相反的事**——先分清：

| | **固化（真升格）** | **去重（归并清理）** |
|---|---|---|
| 是什么 | 卡里的知识要**搬进**更常驻的载体 | 知识**本来就在**载体里，卡只是副本 |
| 典型触发 | 卡攒够了证据，做成流程或铁律才值得常驻 | **迭代 skill 时顺手吸收了某张卡的内容**（最常见） |
| 前提 | **含 ≥1 次带回新证据的复用**（新边界／例外／修正／捷径） | **确认卡里已无独有内容**（只剩验证记录／来源即达标） |
| 阈值 | 按下表分档 | **无阈值**——与复用次数无关 |
| 动作 | 三件事（见下），**要改 skill** | 改标「已去重 → 指针」＋压缩正文＋同步索引与回执，**不改 skill** |
| 用户确认 | **必须** | **必须**（改的是"这知识以谁为准"） |

> ⚠ **纯检索型复用不计入阈值。** 每次只是"照着同一份清单再核一遍"、备注里没有新信息的复用，
> 只记次数、不推进阈值。**次数只是"有新证据"的代理指标**——代理一旦失效（3 次核同一份清单＝零新增信息），
> 阈值就没有意义。实测教训：某卡复用 3 次**全是检索型**，按旧阈值"≥3 次"就该升格，
> 但该做法早已完整存在于某 skill 里——那是**去重**，不是升格。

**固化阈值（按形态分档）**

| 形态 | 判据 | 去向 | 阈值 |
|---|---|---|---|
| 独立 skill | 有独立触发场景、需打包分发 | `~/.workbuddy/skills/<名>/` | ≥5 次**且**跨 ≥2 个工作区 |
| **并入已有 skill 流程内部** | 不是独立场景，而是某个已有流程的**一个步骤或闸门** | 改写那个 SKILL.md | **≥3 次，且其中 ≥1 次带回新证据** |
| 写入长期记忆 | 是铁律／偏好／口径，不需要流程编排 | `~/.workbuddy/MEMORY.md` | ≥5 次**且**跨 ≥3 个会话 |

**固化必须经用户确认**，绝不自动改写既有承载文件。

**固化＝同一批次的三件事，缺一不可**：

| # | 动作 | 是否改 skill |
|---|---|---|
| ① | **写进载体**（skill ／ 全局 MEMORY ／ 原理层手册） | **改** → 须同步升版本号（号由用户指定） |
| ② | 原卡改标「已升格 → 指针」，正文压缩为 **载体里没有的那部分**（验证记录／实测证据／升格去向／来源任务） | 不改 |
| ③ | 同步 `_索引.md`、`复用回执`、工作区 MEMORY | 不改 |

⚠ **只做 ① 会留下"两处并行"的中间态**——同一知识在载体和卡里各存一份，
且**没有任何标记说明该以谁为准**，后续会话读到卡会照卡执行。
**若在重构／迭代 skill 时顺手吸收了某张卡的内容，当场就要补做 ②③（且这是"去重"，不是升格）。**

> 索引里须写明读取纪律：**标「已升格／已去重」的卡不再按正文执行，以载体为准。**

#### 判阈前的输入体检（2.1.0 新增，**必做**）

**为什么**：阈值的输入是「复用次数」，而这个数字长期不可信——实测三源打架：
索引「复用」列与回执实际出现次数对不上（个别卡索引记 3、回执实际 15），且**部分卡根本没有「复用记录」字段**。
（⚠ 卡内「复用记录」字段**已于 2.4.1 移除**——次数一律由回执聚合、落索引「复用」列；此处保留的是历史实测。）
**输入不可信 ⇒ 阈值形同虚设 ⇒ 归并时只能凭感觉、于是被跳过。先修输入，再谈触发与留痕；顺序反了会做无用功。**

1. **跑 `assets/回执统计.py`**（默认 dry-run，只报不改）：
   - 输入＝工作区根目录（默认当前区）；输出＝逐卡「回执出现次数 ／ 含新证据次数 ／ 是否达阈 ／ 索引现值对不对」
     ＋ **被排除行清单**；`--apply` 才回写索引「复用」列（**索引降为派生视图，不再手写**）。
2. **口径三条**（脚本已实现，人工复核照此判）：
   - 只统计**回执表格的数据行**，且只从**卡片ID 列**取号——备注里的顺带提及不算；
   - 卡片ID 列标「本次新建／建库，非复用」的**不计次**（那是产出，不是复用）；
   - **纯检索型复用不计入阈值**（照同一份清单再核一遍、无新信息的，只记次数）。
3. **`新证据` 枚举列**：回执表新增一列，值只有 `有`／`无`。
   **散文备注聚合不出来，枚举值才可脚本判**——「方案闸」列之所以真被用起来，正是这个道理。
4. ⚠ **口径坑**：别处回执里的「✓＋升格」可能指**卡内加章节**（实测：某区 2 行即此情形），
   **不是**「卡 → 载体」升格。**同名异义，统计前先确认口径。**

#### 悬挂台账：暂缓 ≠ 否决（2.1.0 新增）

**问题实测**：某卡被判「已达升格阈值，用户决定先补卡、暂不升格」；此后它又被复用 **≥5 次**，
而**索引「复用」列没更新、等级仍写「草稿」**——**今天没有任何人能从磁盘看出它早该升格。暂缓＝遗忘。**

- **文件**：`经验库/_台账.md` 的**类型＝待升格**行（每类 ≤10 行，格式见 `assets/台账模板.md`）。
- **写入时机**：判出「已达阈值但未获批准」时**当场录入**（收尾必报同句报、归并时也查）。
- **字段**：`卡号 ｜ 卡在讲什么 ｜ 复用（次数·新证据） ｜ 达阈日期 ｜ 建议去向 ｜ 卡在哪`。
  ⭐ **「卡在讲什么」列强制**（2.1.1 补，2026-10-03 用户反馈）——**只写卡号，用户无法判断**。
  台账是**决策用**的表，不是索引：**只给标识符等于没给信息**。一句话写完「卡解决什么问题、怎么做的」。
- **清理**：批准升格或判定去重后从台账移除，并在回执留一行。
- ⚠ **别把「暂缓」写成卡上的标记就了事**——卡自己不会提醒你。

#### 三形态终点（2.1.0 定界，与全局红线对齐）

| 形态 | 可否自动执行 | 处置 |
|---|---|---|
| **并入已有 skill 流程内部** | ✅ **唯一可自动执行路径** | 判据 ≥3 次且含 ≥1 次新证据；改前先加载 `skill-release-spec`，版本号**由用户拍板** |
| 独立 skill | ⚠ **需用户提供跨区线索**才启动 | `experience-loop` 是**单区** skill、看不到别区卡；**跨区索引已被用户否决** ⇒ 不主动建跨区视图 |
| 写入全局 `~/.workbuddy/MEMORY.md` | ❌ **AI 不执行** | 与全局红线一冲突（**AI 不判断"这条能否进全局"**）⇒ **只记进 `_台账.md` 的待升格类，由用户自己决定** |

**留痕**：不新开列——用 `新证据` 列的**连续「无」**承担（**连续多次「无」＝机制在空转**）。

#### 下沉（长期记忆 → skill／经验库，方向 ↓，2026-09-21 增）

长期记忆**每会话必进、容量最贵**，所以它只该放**铁律与指针**。
命中**任一条**即候选下沉（**只报不改**）：

| 下沉信号 | 说明 |
|---|---|
| **适用面收窄** | 只在某一类任务里才会被引用（如 skill 表头字段 → 只在改 skill 时） |
| **是参数不是铁律** | 具体数值、字段清单、量值、路径（铁律可常驻，参数必下沉） |
| **单节 >15 行而核心只有一句** | 长节＝细则堆积，细则属于 skill |
| **已有同主题 skill** | 有家可搬，没理由常驻 |

**下沉 ≠ 删除。** 必须同时做**三件安全网**：

1. **入口行常驻** —— 在下沉处留一行「**何时触发 ＋ 一条红线 ＋ 去哪取**」。
2. **反向指针** —— 承接方写明「本节由 `MEMORY.md` 于 <日期> 下沉而来」，可追溯。
3. **可整段还原** —— 下沉时把原节全文备份进 `backup_<日期>/`，说一句就能贴回。

**下沉后的触发保障（四层，缺第三层就会"该用时想不起来"）**：

| 层 | 机制 | 作用 |
|---|---|---|
| ① | 承接 skill 的 `description` **写全触发词** | 平台自动加载 |
| ② | 其它 skill / 文档遇相关处写**指针**"见 skill X" | 自动匹配没命中时的兜底 |
| ③ | **长期记忆里保留一行入口** | **唯一保证「任何会话都能触发」的一层** |
| ④ | 说「记忆体检」复查已下沉内容与入口 | 人工复核 |

> 口诀：**把"常驻内容"换成"常驻入口"** —— 行数 22 → 1，触发能力不降。

注意：**升格是本机制里唯一跨出「单工作区」边界的动作**——工作区结构、经验库、复用回执
都是单工作区机制，只有升格会离开本区。别把跨区内容塞进前两段。

**跨工作区引用卡号时必须自包含**：`E-XXX` 是**工作区本地编号**，同一个号在不同工作区
指向完全不同的内容（实测：同一个编号在不同工作区分别指向互不相干的卡）。
跨区引用一律直接写出做法要点，或写全路径（`<工作区>/经验库/方法论/E-001.md`），
**不许只写裸卡号**。

## 维护 · 语义盲评（2.5.0 新增；触发：「归并经验库」「记忆体检」；**升格／合并动作前必做**）

**治什么**：判重／判过期这类**语义判断**，过去是在"写卡的同一会话里顺手做" ⇒ 与写卡**同源**，
会不自觉为自己写的卡说话。**评分者不能是被评者。**

**怎么做到真「盲」**：
1. **用子代理** —— 叫一个**上下文干净的子代理**，只给它「卡文件路径 ＋ `_索引.md`」；
   它**天生看不到**主会话写卡时的推理链。这是**技术上可执行的输入隔离**，不靠自觉。
   （子代理不可用时退一步：**先判、后改**，把"判"与"写"在时间上拉开。）
2. **诚实定界**：这不是"换一个模型／裁判"，而是**输入盲化**（蒙眼）。
   独立性的来源 ＝ **只看成品、不看过程**。**别把它说成"另一个裁判"。**

**两级触发（不做每日跑）**：

| 级 | 何时 | 范围 | 理由 |
|---|---|---|---|
| **L1 前置闸** | **任何升格／合并动作之前** | 单卡（1–2 张） | 升格是**不可逆的信心跃升**，必须过一次独立眼 |
| **L2 批量** | 「归并经验库」「记忆体检」时 | 全部**草稿**卡 | 归并本就是判重的高频点，顺带做、不额外开会话 |

**输入白名单／黑名单（盲化边界，必须写死）**：

| ✔ 允许 | ✘ 禁止 |
|---|---|
| `经验库/_索引.md` | 写卡时的对话记录 |
| 待判卡正文 | 本次任务的 `_方案.md` |
| 疑似重复的**对照卡**正文 | 卡作者的自述理由 |
| 相关 skill 的对应章节 | **该卡的历史复用回执**（防"用得多＝好"的锚定） |

**输出四段（≤20 行，与研讨卡同规格）**：
1. **结论**：`保留`／`合并到 E-0YY`／`降级`／`标失效` —— 四选一，不许含糊；
2. **依据**：引用**卡内或载体的原句**（必须可点）；
3. **反证**：有没有哪一处**只在载体里、卡里没有**（判「可去重」的关键一问）；
4. **存疑**：拿不准的写明，**不许硬下结论**。

**结果三出口**（判断必须有落点）：保留 ＝ 不动；合并／降级 ⇒ 写进 `_台账.md` 的待修订类或改标签，
**改动一律由用户拍板**（红线：AI 不改既有 skill、不判"能否进全局"）。

**防形式主义三招（决定它会不会变成空转）**：
1. **必留痕** —— 盲评卡落盘（任务目录或归并报告），否则无法核查真做过；
2. **可抽检** —— 用户可随机抽一张核对「结论 ＋ 依据」；**不成立 ⇒ 该批作废**；
3. **「全保留」触发抽样复核**（3.0.0 改）—— 一批盲评若 **100% 结论是「保留」**：
   **随机抽 1 张人工核对「结论 ＋ 依据」**；**核不成立才作废该批**，核成立则该批有效，
   但在归并报告里记一行「**本轮全保留，已抽样复核**」。
   （理由：对一个本就健康的库，全保留是**合法结果**——旧口径「全保留即失效」会**误杀真健康的库**；
   保留 `E-014`「整齐的异常是筛选器出错的强信号」的**警觉**，去掉刚性误杀。）

**成本**：一次 1–3 张卡、几百到 1–2k token；子代理独立上下文、**不污染主会话**；**不新增常驻内容**。

## 维护 · 记忆体检（用户触发：「记忆体检」）

**只报不改**，输出双向清单：常驻记忆里该下沉的 ＋ 载体／经验库里该升格的。

### 盘点：对账「索引 ↔ 载体」（2.3.0 新增 · **记忆体检的第一步**）

**做什么**：报四类事实——**这是本机制原有两个脚本都不查的那一块**
（它们查「**部件在不在**」「**账填得合不合法**」，不查「索引指着的卡还在不在、
指针指着的载体里到底有没有那段知识」）。
**根因案例**：一次下沉事故（当时最贵的一笔代价）——「**下沉前必须先 grep 源 skill**」，
正是因为当时**只能人肉 grep**，没有任何机制能机械证明"载体里真有这条"。

| 结果 | 含义 | 危险度 |
|---|---|---|
| **Missing** | 索引有行 → 卡文件不存在 | 检索会命中一个空指针 |
| **Orphan** | 卡文件存在 → 索引无行 | **检索永远找不到它 = 等于不存在** |
| **Stale** | 标「已升格／已去重」→ 载体里查不到该卡的关键词 | **知识静默丢失** |
| **无法判** | 载体识别不出且全库无命中 | **不臆断为 Stale**，交人工确认 |
| **等级越界** | 「等级」列的值不在封闭值域内（2.4.0 补） | 词一乱，脚本只能靠猜 ⇒ 判据失效 |

**附加产出（2.4.0 改-4）**：同一支命令加 `--carriers` 即**派生载体总表**
（`知识 → 载体`，**只列已升格／已去重**的卡；`--carriers-out <路径>` 可直接落成 `经验库/_载体总表.md`）。
它回答一个原来**没法机械查询**的问题：「这条已升格的知识，现在住在哪个载体里？」
⚠ 关键词偏通用时会命中多个技能 ⇒ 表里给**命中数最高**的那个为主，其余记候选。

**怎么跑**：`python3 <skills>/experience-loop/assets/索引一致性检查.py <工作区根> [--report <明细路径>] [--carriers [--carriers-out <路径>]]`
——**只读**，不改任何文件；**对话里只读摘要与 Top 5，明细落盘**（Token 纪律）。

⭐ **「定期」怎么落地——用台账，不用定时器**：

1. 结果写进 `经验库/_台账.md` 的**类型＝盘点**行（格式见 `assets/台账模板.md`；每类 ≤10 行），核心字段是 **`上次全量盘点日`**；
2. 该日期是**「记忆体检／归并」的第一步硬闸**：**距今 >30 天，或卡片数增量 >10 ⇒ 先跑全量盘点，再干别的**；
3. 于是「定期」**不依赖定时器、不依赖记性**，只依赖一个**能被脚本读的日期**。
   ⚠ **默认不设定时任务**：无人值守会话**过不了闸门 G**（「停下等批复」会卡到超时），
   且**输出没人看 ＝ 白烧一个会话**（比不跑更糟——你会以为跑过了）。

**除记忆体检外，还有三处应「当场」补跑**（一致性只在**改动的那一刻**坏掉，不在某个日历日）：

| 时机 | 会怎么坏 |
|---|---|
| **升格／去重之后** | 索引改成指针了，但知识**可能没真搬进载体** ⇒ Stale |
| **skill 改版之后** | 载体章节变了 ⇒ 老指针**悬空** ⇒ Stale |
| **清理／归档之后** | 卡被搬走、索引还记着 ⇒ Missing |

⚠ **两条纪律**：① **Stale 是弱判据**（同义词会漏报）⇒ 报出来的**一律人工核一遍再动手**；
② 本环节**只报不改**，修索引／改载具一律另起动作、由用户拍板。

### 截断体检（2026-10-03 新增，必查项）

⚠ **常驻记忆不是"写全了就生效"——服务端会在注入时截断，且按字符位置盲切。**

实测：全局 `~/.workbuddy/MEMORY.md`
服务端**只注入前约 4,200 字符**（样本中恒定，末尾带 `... (user memory truncated)`），
超出部分**不按语义分段**，直接从第 N 字符一刀切下。

**三个后果**：

| 后果 | 说明 |
|---|---|
| **章节顺序决定生死** | 越靠后的规则越可能从未进入上下文，而写的时候完全看不出来 |
| 截断点落在章节中间 | 实测曾切在某个章节的中间，前半生效、后半失效 |
| "写了等于没写" | 被切掉的章节在磁盘上存在，但**从未参与任何一次推理** |

**体检必做三步**：

1. **量实际注入量**——不量磁盘大小（磁盘可能远超上限，尾部全是死重）。
   取**实际落盘的那份 prompt 文件**里 `<user_memory>` 块的字符长度即为注入量
   （该文件在本机的落盘位置见本节末「平台适配点」）。
2. **逐条核对位置**——每条常驻规则的起点是否 < 上限。越界的分两类：
   - **事故级红线**（漏了会返工／丢数据）→ **前移 ＋ 压缩**，绝不删；
   - **其他** → 走下沉三件安全网。
3. **留余量**——上限是服务端定的、可能变。设计时按 **70%** 留余量（本机即约 3,000 字符）。

### 判据是"漏了会不会出事"，不是字数

**不要设硬性字数闸**（如"超 3,000 字符就删"）。硬闸会逼模型压缩措辞，
**丢掉的往往是最重要的限定条件**——"必须先读磁盘最新版"里的"先"、被省略的例外、
"仅当用户明确要求"里的前提。压缩过程本身就是质量损失。

正确顺序：**先按后果分三档**（事故级／有时效的流程信息／沉淀知识），
只对第三档做下沉，第二档压缩，第一档前移。

> **实战一例**：用户级 MEMORY.md 有三章事故级红线躺在被截断区，**长期从未生效**——
> 而它们的知识在别的工作区都有副本（知识没丢，模型不知道）。
> 处理方式不是删，是**前移 ＋ 按「触发→红线→去哪取」三段式重写**，
> 总量降约 35%，三条红线全部落进注入上限内。

### A3 双层分工：长期记忆 vs 工作日志（2026-10-03 新增）

工作区记忆目录 `.workbuddy/memory/` 下有**两个性质完全不同的文件**，别混：

| 文件 | 性质 | **是否进上下文** | 怎么写 |
|---|---|---|---|
| `MEMORY.md` | 精选长期事实 | ✅ **每会话注入** | 只放**跨任务还会再用**的；细则下沉 |
| `YYYY-MM-DD.md` | 当天工作记录 | ❌ **不注入**（读了才进） | **路标式**（见下） |

**写入判据一句话**：跨任务还会再用 → `MEMORY.md`；只跟当天这件事有关 → 日志；
下次同类任务会用到 → `经验库/`。

#### 记忆预算（软上限，不是硬闸）

- **`MEMORY.md` 建议软上限 6,000 字符**（**经验值**）；到线即**跑一次记忆体检**，**不是自动删**。
- 与全局规则（硬上限约 4,200，**实测**）不同：工作区记忆**实测超过 4,200 仍未被截断**，真实上限未知
  ⇒ **只给信号、不设硬闸**（判据仍是"漏了会不会出事"）。
- **"放不下"的解法不是扩容量，而是往下沉一级**：区级 `README_…`／项目级 `README.md`／
  `_索引/`／`经验库/`——按"**我多久用一次**"选层。

#### 日志写法：路标式

日志的价值是**时间轴回溯**（"上个月那件事怎么处理的"），不是正文流水。

- **一行一件事**：`## <原章节标题>` ＋ 一句「结论／关键结果」
- **留住**：结论、决策、口径、坑、遗留，以及**关键数字与坑名**（让读的人不必翻归档就能"看见"要点）
- **不留**：过程叙述（"走了 A→B→A"）、命令流水、逐条 diff、脚本内部细节
- **指针必须可点**：只写**真实存在**的路径；不确定的写成普通文字，**不要用反引号伪装成路径**

⚠ **为什么必须改**：实测全仓日志**上百个、总体积 MB 级，单日最高近 5 万字符**。
注意这**不是上下文成本问题**（日志不注入），而是**"读历史时一次读爆"**——
想翻某天做过什么，一天就吃掉大半额度。

**存量瘦身 ＝ 「路标版 ＋ 完整归档」（2026-10-03 用户拍板 A 版）**：

- **原位只留路标**：章节标题 ＋ 一句结论，压到原文 **5–10%**（实测三份均落在该区间）。
- **原文完整归档**到 `memory/归档/YYYY-MM-DD_全.md` —— **这才是「零丢失」的落点**：
  零丢失 ＝ **原文在归档里**，**不是**"路标版里包含全部信息"
  （上一版正是这里含混，导致压到 91% ＝ 形同没压）。
- **顺序**：先归档并**校验 md5 一致**，再覆写原位；扫描与动手分两轮（守下文清理红线）。
- **指针校验**：逐条 `os.path.exists`；**通配符与省略号一律不算指针**。

**压缩的代价与三条缓解（2026-10-03 补）**：

压缩会损失**偶遇性知识获取** —— 原来读日志会"顺手"看到细节，路标版只有结论，
而 **AI 不会主动去翻归档**（它不知道下面还埋着东西）。三条缓解：

1. **该复用的必须沉淀进经验库／口径卡** —— 日志从来不是知识载体；
2. **路标结论要带关键数字与坑名**，让读的人不必翻归档就"看见"要点；
3. **文件头写明归档路径**，需要时知道去哪翻。

**「细节进经验库」＝一次筛选（2026-10-03 用户定）**：

新写法的形态是「**当天把细节写进任务目录／经验库候选，日志只留路标**」——
**不能反过来指望"当天随便写、以后再补完整版"**：未来日志若只写路标，就没有完整版可归档。

而"哪些细节够得上进经验库"**本身就是一次筛选**：
**由 AI 筛、也由 AI 决定入不入**；但**收工必须汇报"入了什么、为什么"**，
**用户保留否决权 —— 不否定即代表没意见**（见 ③ 段收尾档第 6 步）。

## 维护 · 版本对齐（老区升级；触发：「升级工作区」；「记忆体检」时顺带报差异）

**治什么**：技能迭代到新版后，老工作区停在旧版形态——机制**静默缺席**（缺 `_台账.md`）、
格式过时（老回执提不出新数据）、或形同"已经修过"的问题在新判据下复发。**都不报错，所以没人发现。**
（与「静默失效」同族，只是观测维度从"环节"换成了"区形态"。）

⭐ **核心原则：对齐，不是追平。** 老区差异先分四类，**只有两类要动手**：

| 类型 | 例 | 处理 |
|---|---|---|
| ① 豁免级 | 任务文件夹老结构、领域聚合轴、**机制生效年代之前**的历史痕迹 | **不动**（技能已明文"既有轴一律不动"） |
| ② 懒获得级 | 回执新列、效果 `·闸/·评`、产出物类型前缀声明 | **历史件原样；当月或下一次触碰时用新格式**（回执按月分文件 ⇒ 逐文件升表头即可） |
| ③ 补缺级 | `_台账.md`、`_载体总表.md`（派生）、`ARCHIVE.md` 缺失段与版本标记 | **零风险**：新建／脚本派生／加段 |
| ④ 静默失效级 | 索引首列格式、回执表头列名不含脚本认的键 | **优先修**——不报错的差异最危险 |

**第一步硬闸**：先读 `ARCHIVE.md` 的「**架构版本**」行。
有且已是当前版本 ⇒ 只需轻量对账（格式漂移可在对齐之后再生）；**无标记或落后 ⇒ 跑完整特征对账**。

**特征对账清单（只读；逐项扫区）**：

| 检查项 | 当前要求 | 老区常见差异与后果 |
|---|---|---|
| 台账 | `经验库/_台账.md`（三合一） | 缺件 ⇒ 升格悬挂／待修订无落点；有旧件 ⇒ 内容搬家、旧件归档 |
| 载体总表 | `_载体总表.md`（派生） | 缺件可**缓建**——无升格／去重卡时生成＝空表，待到首次升格再派生 |
| 归档契约 | `ARCHIVE.md` 五段 ＋「架构版本」行 | 缺「类型表」段 ⇒ 产出物分类无契约依据 |
| 回执行 | 表头含脚本认的键（效果／有用、新证据、检索、方案闸） | **列名自创（如 `✓/△/✗`）⇒ 效果列被读作「未评」**——静默丢效果数据 |
| 索引 | 首列纯文本 ID | 链接式 ⇒ 整区被跳过、盘点误报（2.4.2 实锤） |
| 安全层 | `_隔离区/`、`.workbuddy/archive/` | 按需建；**做清理前必建** |
| 任务痕迹 | `_说明.md` 含「关联经验卡」行 | **机制生效前的历史任务＝合法豁免**；生效后的缺痕才处理 |

**迁移图谱（只列"会改变老区动作"的版本；写明"无"也是资产）**：

| 版本 | 结构级变更 | 老区动作 |
|---|---|---|
| 2.1–2.3 | 台账类文件出现（`_待升格.md` 等） | 3.0 之后统一：有旧件→搬家；无→直接建 `_台账.md` |
| 2.4 | `_载体总表.md`（派生）；索引首列规范 | 派生生成；查索引首列格式 |
| 2.5 | 效果列有据化（`·闸/·评`） | **无后缀自动按 `·评` ⇒ 老行兼容、无需动** |
| **3.0** | **台账三合一**；回执拆列；任务文件夹统一 | 搬家／建档；回执**懒获得**；结构**豁免** |
| 3.0.1／3.0.2 | 归档五段（＋类型表）；`_类型清单.md` | 补段；清单按需生成 |
| 3.1–3.4 | 工具补丁集；吸收型；触发词口径 | **无**（老区无需动） |
| **3.5** | 本机制自身（版本对齐） | **可选**：跑一次对齐；不跑不影响既有运行 |

**无损五纪律（全部复用既有资产）**：

1. **两轮分离**（同整理清理）：扫描＋差异清单**只读**完成、汇报后，用户明示才动手；
2. **改前备份** `.workbuddy/backup_<日期>/`；旧件不删——入隔离区或归档层；
3. **只增不改旧文**：加段不动旧段；升格式只动表头／注释，**数据行不动**（旧行少列按原样、不重写）；
4. **改后校验**：逐文件 diff ＋ 重跑对账三件（索引一致性／回执统计／痕迹检查），确认**无回归**；
5. **留痕**：区 `.workbuddy/archive/` 记**对齐日志**（变动清单＋备份对应＋校验结果＋**回滚方法**）。

**完成判据**：① 对账脚本**无回归**；② 新机制至少**被真实使用一次**（"部件存在"不算）；
③ `ARCHIVE.md` 版本标记已更新。**范围定界**：本段只动"机制形态"（补件／换格式／标记），
**不做文件搬移与清理**——那属「整理归档与清理」节。

**发版约定（与 `沿革.md` 互为表里）**：每次技能发版，在沿革版本块末标一行
「**对存量区的影响：无／补件／换格式／改名（哪些文件）**」＋一行「**判据回归：跑没跑、结论**」
——本图谱即由此汇总；**没有这两行，下次升级只能靠回忆、改判据也只能靠感觉**。
⚠ **判据改动的回归口径**（改闸门G 分级判据／升格阈值／表头列名时必须跑）见 `tests/预期输出.md`「判据改动的回归口径」节——
**不新增常设机制**，只在发版时多跑三条命令（存量区直通率／达阈清单／对账三件）。

> 首例实证（某工作区）：全量对账出 8 项差异 ⇒ **实际动手仅 3 项＋微调 1 项**——「对齐 ≠ 追平」成立；
> 其中"回执表头列名自创"一项属④（真静默失效），修复后重跑全部无回归。
> 同批全仓扫描另证：多数有库区**缺 `_台账.md` 等新机制**——老区主形态是**缺件**，不是旧件待搬。

## 维护 · 效果体检（触发：「效果体检」「这个 skill 到底有没有用」；**归并经验库时顺带做**）

> **来源**：`E-009`「跨工作区 skill 效果体检法」于 **2026-10-03** 经用户拍板升格并入（形态二）。
> 原卡已改标「已升格 → 指针」，只留验证记录与实测证据；**操作以本节为准**。

**适用**：某个用户级 skill 已在 **≥3 个工作区**跑了 **≥2 周**，要回答「它到底有没有用、哪一段在空转」。
**信号**：只能说出"我一直在用"，说不出用量、失败率和失败模式。

**总判据（一句话）**：**判"机制有没有被使用"，不看目录存不存在，看日志里有没有它的产物** ——
回执、索引、隔离区日志是**机制自己留下的脚印**，比任何自述可靠。**只取磁盘证据，不凭记忆、不先问用户。**

**九步**（前 8 项查"**部件是否存在**"，第 9 项查"**通道是否连通**"）：

1. **逐区列机制部件**：经验库／索引／复用回执／归档契约／任务文件夹——存在与否、体量多少。
2. **看命名判「挂载是否真执行」**：机制目录用了**该区既有命名**（如 `_经验库`、描述性卡名而非 `E-XXX`）
   ＝「① 立架构」的探测步**真跑过**；各区一律默认名，反而是模板硬套的信号。
3. **量复用规模**：回执行数 ÷ 涉及任务数；再看**单卡最高复用次数**（集中度）。
4. **量索引是否失控**：条数、平均行长、有无超长行（索引是**每次任务**的固定成本）。
5. **验升格闭环**：被升格的卡**是否已压成指针**、承接方**是否有反向标注**——
   **两处并行**是这套机制最容易留下的暗伤。
6. **验安全层**：隔离区批次与迁移／删除日志是否存在、批次是否超期未清、有无 `rm` 痕迹。
7. **补三张反证**（`grep` 就能做）：有没有「不硬凑／未匹配」的**实际运用记录**；
   可选机制（如校准台账）是否**只建在合适的工作区**；老区是否缺归档契约。
8. **审脚本护栏——文档看结构、脚本看护栏，两者不能互相代替**：
   - **路径护栏**：写操作是否对 `src`／`dst` 做 `realpath` 并校验**落在 `realpath(root)` 前缀内**
     （`os.path.join(root,'../../x')` 与绝对路径都能逃逸）；
   - **幂等可控**：日志有没有 `batch` 字段、回滚能否**只回滚当次**而非全部历史；
   - **黑名单覆盖面**：是否在**所有**子命令生效，含 `rollback`／`restore` 这类"往回写"的路径；
   - **自检判据**：把脚本与上一版**做字节比对**——字节相同＝未改动，别凭"我记得改过"。
9. **审「消费端」——产物有没有被消费的通道**：产物写出来了，**下一个人／下一个会话靠什么找到并使用它**？
   查法两条 —— ① 抽若干产物，看内部有没有**自包含的可执行入口**（如一行可复制的启动／接手口令）；
   ② 外部索引（README／目录／工作区根）**实际**有没有指向它的指针 —— **`grep` 确认，不信"我写了"**。

**补一项检查 · 判据实现要拆四段（2026-10-15 并入）**：凡带"处置"语义的判据（「按 X 计」「排除」「归为 Y」
「降级」），拆成 **触发 → 检测 → 处置 → 留痕** 四段——**四段必须落在同一层可执行代码里**。
**只告警不处置＝假指标**：告警本身成了"已处理"的证据（检测做了、处置静默缺失——比"整段没做"更危险）。
验证**必须用反例断言"后续计算结果真的变了"**，不能只看有没有告警（只看告警＝没验）。
实测：某规则文档写了、代码只告警 ⇒ 机械证据覆盖率虚高（70% vs 真实 60%），靠 `E-010` 式反例回归才抓出。
⚠ 刻意「只报不改」的场景（先出清单、再人工决定）**不算失效**，但**输出里必须写明"只报不判"**。

**坑与边界**：

- **只看文档 ＝ 半个体检**：带脚本的 skill **必须单独过一遍输入校验**（实测本区自评只查文件与目录，
  漏掉"越界搬移可逃逸 root 前缀""`rollback` 无批次字段"两处）。
- **日志里的历史版号不算"漂移"**（那是沿革，应当保留）；只有**现行文档**（`MEMORY.md`／`ARCHIVE.md`／
  README／交接文件）里的**当前态快照**才算漂移。
- **别把"没跑"直接判成"失效"**：先看该区**近两周有没有新任务**——没有任务的区，机制空转是正常的。
- 体检结论**只报不改**；改 skill 需另起方案，并由**用户拍板版本号**。

> **一般规律（第 9 项挖出的）**：**只定义"怎么写"、不定义"怎么读"的技能，会把全部摩擦堆到消费端**，
> 而**产出端的达标率会掩盖这个问题**（当时交接产物的行数达标率很高，看起来非常健康）。

## 维护 · 整理归档与清理（用户触发）

**四阶段不可逆梯度**：D0 只读扫描 → D1 只读诊断出方案 → D2 可逆搬移 → D3 不可逆清理。
**铁律：扫描与动手必须分两轮对话**——D0＋D1 在本轮做完即停下汇报，用户明示后才进 D2／D3；
**禁止同一轮里既扫描又删除**，这是误删的最大来源。

### 第 0 步 · 先判「这是什么」（产出物类型体系，3.0.1 新增）

**整理的第一步不是找垃圾，是给文件判类型。** 没有类型维度时，判据只剩「能不能删」，
而「能不能删」是「这是什么」的函数——上游缺失，下游只能临场判断（**隔离区因此退化为"没有类型信息的黑洞"**）。

- **8 类值域封闭**：交付物（含数据）／过程稿／脚本／说明与规则／机制台账／备份件／编译副产物／原始材料；
  **排除集**：应用内部残留。全表见 `assets/清理手册.md`「〇之三」节。
- **判定顺序 6 步不可换**：`排除应用残留 → 排除原始材料 → 声明 → 名字/扩展名 → 目录兜底 → 保守默认「过程稿」`。
- **声明为主**：任务 `_说明.md` 的「产出清单」里加类型前缀（`- [交付物] 报告.docx —— 说明`），**不新增结构**。
- **工具**：`python3 <skills>/experience-loop/assets/产出物分类.py report --root .`（只读对账，含「疑似原件」与
  **「疑似旧版组」**两个待确认清单）；`quarantine-list [--commit]` 为隔离区批次出 `_按类型清单.md`（**不动文件路径**）。
- ⭐ **可见形态**（3.0.2）：`folder-lists [--commit]` 给**每个任务／主题文件夹**生成一份 `_类型清单.md`
  （`_` 开头排最前，打开文件夹第一眼可见）。⚠ **只有落到用户每天会打开的文件夹里，类型才算真落下来**——
  报告写进任务目录＝只对 AI 可见（实测教训：跑完 D0 后用户的原话是「**为什么我看不出来**」）。
- ⚠ **不做静默自动降级**：同族多版本里混着原始材料的**并列多份**（多份证书／多年报表／多张截图），
  机械「取最新」会误杀 ⇒ 只**列出**「疑似旧版组」，由用户确认后再降级。

**判据三条**（全表见手册）：**L1** 可再生文件（0 字节／`.DS_Store`／`*.tmp`／`node_modules`／`__pycache__`）
→ 清，**仍先进隔离区**｜**L2** md5 完全重复、或已有更新版本的「副本·old·备份」→ **逐项勾选才删、判据可举证**｜
**L3** 大文件／久未动／名字像废弃 → **永不自动删**。
**能力边界**：AI 只判得出"两个文件内容是否相同"，判不出"这个文件还有没有用"——**宁可留着不删，不可误删**。
**领域聚合型的既有文件夹一律不动**（既有轴优先于整齐）。

**五道红线**（D3 强制执行，原文见手册）：① 隔离区优先、**禁用 `rm`**（移入 `_隔离区/YYYY-MM-DD/` 保留 30 天）；
**`purge` 是唯一物理删除**——**不经回收站、不可恢复**，执行前必须 dry-run 预演、人工核对批次清单，
且逐文件先写入删除日志（⚠ **`--days` 须 ≥1**；按批次精确清用 **`--batch`**，可复现、不依赖"今天几号"）
② 黑名单豁免（`.workbuddy/`、`上传材料/`、`经验库/`、`复用回执/`、`.git/` 及任务目录下的用户原件）
③ dry-run 默认 ④ 搬移／隔离每批 ≤10、删完校验、失败即停（**`purge` 是批次粒度**，批次规模应在 `quarantine` 阶段受控）
⑤ 迁移日志＋删除日志双留痕（**`--commit` 自报覆盖率**）。

> **3.1.0 补丁集（P1–P6）**：`--days` 下界校验／`purge --batch`／`move` 允许从隔离区取件／
> purge dry-run 增距今天数与**可读文本警示**／`scan` 点名隔离区／`restore` 按日志还原**原名**。逐项见 `references/沿革.md`。

**D0–D3 各自怎么做、脚本全参数、`map.json`／`list.txt` 格式、出方案与停批复的节点，
全在 `assets/清理手册.md`——执行本段前先读它，此处只留判据与红线。**

## 附 · 平台适配点（3.0.0 新增：换平台前先看这里）

> **换平台时最危险的不是报错，而是"不报错、只是查不到东西"** —— 这正是本 skill 最警惕的静默失效。
> 下表四行是必须在迁移时**重新标定**的东西，不要直接搬数值。

| 机制 | 本机（WorkBuddy）实测 | 迁移时需重新标定什么 |
|---|---|---|
| 记忆注入上限 | 全局 ≈4,200 字符、**按位置盲切** | **必须重新实测**——上限与截断策略都由平台定 |
| 落盘 prompt 位置 | **本机专属**（不写死字面路径；以 CLI 日志 `systemPromptFile=` 指向的落盘文件为准） | 新平台的落盘位置；脚本可用 `EXP_LOOP_GLOBAL_MEM` 覆盖 |
| skills 目录 | `~/.workbuddy/skills/` | 新平台目录；脚本已支持 `EXP_LOOP_SKILLS_DIR`，**目录缺失时显式告警、不再静默查空** |
| 子代理能力 | 可用（**语义盲评依赖它**） | 新平台是否支持干净上下文的子代理；不支持则退化为"先判后改" |
| `rm` | **是坏 shim** ⇒ 一律用 Python `shutil` | 新平台 `rm` 是否可用、是否走回收站 |
