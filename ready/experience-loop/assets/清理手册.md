# 整理与清理 · 操作手册

> 本文件是 `experience-loop` 的**按需加载附件**——只在真正执行整理/清理时读（**执行前必读**）。
> SKILL.md 的「维护 · 整理归档与清理」段只留**判据摘要与铁律**，本文件保留**判据全表 ＋ 逐项操作细节**。
>
> 脚本路径记为 `$T`（＝ `<skill目录>/assets/整理工具.py`）、`$T2`（＝ `<skill目录>/assets/产出物分类.py`），**一律在工作区根目录执行**。

## 〇、冗余三级判定（全表）

| 级别 | 判定 | 处置 |
|---|---|---|
| **L1** | 0 字节／`.DS_Store`／`Thumbs.db`／`~$xxx` 锁文件／`*.tmp`／`node_modules`／`__pycache__`／`dist`／`build` | 可再生，直接清理（仍先进隔离区） |
| **L2** | md5 完全一致的重复文件；带「副本／最终版／old／备份」且存在更新版本 | 逐项勾选才删，**判据必须可举证**（与哪个相同、新版本是哪个） |
| **L3** | 大文件、长期未动、名字像废弃 | **永不自动删**，只进清单、只提问 |

> **能力边界**：AI 只能判断"这两个文件内容完全一样"，判断不了"这个文件还有没有用"。
> **宁可留着不删，不可误删**——冗余的代价是混乱，误删的代价是数据丢失，两者不对等。

## 〇之二、清理五道红线（D3 强制执行，缺一不可）

1. **隔离区优先，禁用 `rm`**：所有"删除"＝移入 `_隔离区/YYYY-MM-DD/`，保留原目录结构，30 天后才真删。
   **`purge` 是唯一物理删除操作**：**不经过回收站、不可恢复**——执行前必须 dry-run 预演、人工核对批次清单，
   且该批次**每个文件先写入删除日志**（`.workbuddy/archive/删除日志.jsonl`，`op=purge`）后方可 `--commit`。
   本环境 `rm` 是坏 shim，一律用 Python `shutil.move`／`os.remove`。
   ⚠ **`--days` 必须 ≥1**——`--days 0` 会让**全部批次（含当天刚移入的）**都算"已超期" ⇒ **一次删光隔离区**；
   **按批次精确清用 `--batch <批次名,…>`**（可复现，不依赖"今天几号"；与 `--days` 互斥）。
2. **黑名单豁免**：`.workbuddy/`、`上传材料/`、`经验库/`、`复用回执/`、`.git/`、
   任何任务目录下的 `上传材料/`（用户原件）——一律不进待删列表，任何段都不删。
3. **dry-run 默认开**：不加 `--commit` 只打印"将删除什么 ＋ 理由"。
4. **限量分批**：**搬移／隔离**每批 ≤10 个，删完校验，失败即停。
   ⚠ **`purge` 是批次粒度**（整批 `rmtree`，无法逐文件分批）⇒ 本条的"≤10"约束的是**搬移与隔离**；
   **批次规模应在 `quarantine` 阶段就受控**——两条约束的粒度不同，不是矛盾。
5. **双重留痕**：迁移日志 ＋ 删除日志（含 md5）都写进 `.workbuddy/archive/`，
   防止同一文件被反复生成又反复删。**`--commit` 时自报覆盖率**（写入条数 ÷ 批内文件数）——
   「日志文件存在」≠「每次操作都过它」。

## 〇之三、产出物类型体系（2026-10-08 新增 · **先判「这是什么」**）

> 回答「**这是什么**」；**不回答**「还有没有用」——那仍由用户裁决。
> 对账与出清单：`python3 "$T2" report --root .`（只读）／`python3 "$T2" quarantine-list --root . [--commit]`。
> 本节的表与 `assets/归档规则模板.md`「三、类型表」为**同一套**；模板用于新建工作区时落盘。

**8 类（值域封闭）**：交付物（含数据）／过程稿／脚本／说明与规则／机制台账／备份件／编译副产物／原始材料。
**排除集**：应用内部残留（`file-history`／`artifact-index`／`changes-index`／`traces`／`projects` 等，与产出物无关）。

| 类型 | 判据（简） | 落位 | 默认处置 |
|---|---|---|---|
| **交付物**（含数据） | 声明／`产出材料/`／`02_交付物/` | `产出材料/` | 永久 |
| **过程稿** | 声明／`过程/`／`01_过程产出/`／名字含草稿·试算／**默认** | `过程/` | 30 天后可清 |
| **脚本** | `.py/.sh/.js/.ts/.ps1/.bat` | `scripts/` | 随任务 |
| **说明与规则** | `README`／`ARCHIVE`／`_说明`／`_方案`／手册／规范／模板 | 所在目录 | **永不删** |
| **机制台账** | `_索引`／`_台账`／回执／日志／检查点／**`_` 开头** | 机制目录 | **永不删** |
| **备份件** | `.bak`／`backup_`／`_备份`／`压缩前` | 不动 | 30 天后可清 |
| **编译副产物** | `__pycache__/`、`*.pyc` | 不动 | **即可清** |
| **原始材料** | `上传材料/`／`扫描件/`／`00_原始材料`／`.dwg` | `上传材料/` | **永不删** |

**判定顺序（6 步，不可换）**：

```
0 排除应用残留 → 1 排除原始材料 → 2 声明 → 3 名字/扩展名 → 4 目录兜底 → 5 名字 → 6 保守默认「过程稿」
```

> ⚠ 第 4 步「目录兜底」是**段名子串匹配**（不是全等）：`02_交付物/`、`01_过程产出/` 这类**带序号前缀**的
> 命名因此也能判出。**但交付物侧不得用裸「产出」当关键词**——`01_过程产出` 含「产出」，会把过程稿
> 误判成交付物。判据的**唯一真源**是 `assets/产出物分类.py`（3.1.1 起；本表只是它的说明）。

**声明写法**（任务 `_说明.md` 的「产出清单」里加类型前缀，**不新增结构**）：

```
- [交付物] 报告_V07.docx —— 上报用
- [过程稿] 测算_草稿.xlsx —— 中间试算
```

**两条硬纪律**：

1. **不做静默自动降级。** 「更新后旧版自动变过程稿」**实测否决**——同族多版本里混着原始材料的
   **并列多份**（多份证书／多年报表／多张截图），机械「取最新」会误杀。
   走**半自动**：工具列「疑似旧版组」→ **用户确认**后才降级。属性完全可判的只有 `备份件` 与 `编译副产物`。
2. **默认取「过程稿」。** 默认值必须落在**可反悔**一侧（30 天隔离区 ＋ dry-run ＋ 人工核对）。
   代价：未声明前真交付物会被判成过程稿——**偏保守，不是错**。

**隔离区**：保持 `_隔离区/<批次>/<原相对路径>`（**不搬任何文件**），批次内生成 `_按类型清单.md`。

## D0 扫描（只读，零风险）

用脚本扫描，**不要手工 `ls`**——本环境 `find -printf`／`sort -hr` 不可用，一律走 Python。

```bash
python3 "$T" scan --root . [--group-depth N]
```

脚本行为：

- 记录**路径、大小、修改时间、md5**（>50MB 的文件跳过算 md5，避免卡住）
- 自动跳过 `.git/`、`node_modules/`、`.workbuddy/`、`_隔离区/`
- 产出 `.workbuddy/archive/清单.json`，并在终端打印：**总文件数、总体积、类型分布、重复组数**

### `--group-depth N`（分层工作区必看）

`scan` 按路径前 N 层输出「目录分组概览」，每组的**文件数／体积／子目录构成**。
默认 `1`，`2` 下钻，`0` 关闭。

扁平清单看不出"每个组里长什么样"，而 D1 判断任务归属正需要按组的结构视图。
**分层工作区（按项目／标的／客户／站点聚合的）必须看这一节。**

### 两条硬约束

1. ⚠️ **清单 JSON 只由脚本消费，禁止整份读进对话**——几百行路径会一次性吃掉上下文。
   只读脚本打印的统计与 Top 表。
2. **本阶段绝不修改任何文件**。

### ⭐ 全仓（多工作区）扩展（2026-10-15 并入）

用户说「整个目录／所有工作区／不只这一个」时，扫描顺序**不可颠倒**：

1. **先按工作区汇总**（一层目录 × 文件数 × 体积 × 占比）排序，**只下钻 Top2**——实测 13 区 3.94 GB，
   **前二占 96%**，其余合计不足 15 MB（看汇总数字就够，不逐区平均用力）。
2. **大区内按前 2 层路径分组**找集中点（实测某区 3.04 GB 里一个子目录占 75%）。
3. **全仓 `dup` 只跑一次**（同尺寸→md5 分桶，3.9 GB <1 秒），结果**再按工作区归集**。
4. **必查磁盘余量**——余量足（实测 1,730 GB／使用率 8%）⇒ 结论从"省容量"**转向"降认知成本"**。
   **这是最容易给错建议的一步。**
5. 大区常缺机制目录，但属**领域聚合型** ⇒ **不硬搬**，只提示"缺落位规则"。

**专属坑**：`/tmp` 本机**只读**，脚本输出写工作区自己的 `.workbuddy/tmp/`；重复几乎全部来自**解压嵌套**
（判据＝同 md5 的多份路径呈**父子包含**，每组留路径最短一份——落在原件目录仍须用户点头）；
**只看大文件会漏掉最大那一块**（7 个 >50MB 合计 1.19 GB，而 851 MB 重复分散在 277 组小文件里，
**两种口径并看**）。
**执行补充**：可再生清单**先排除 `.pylibs/`／site-packages 等运行环境与 `_隔离区/` 自身**；
黑名单**逐条路径过滤、不整组跳过**，但"同内容另一份落在黑名单目录内"的组**保守不动**；
**隔离区在工作区内部 ⇒ 移动后空间不释放**（30 天后 `purge` 才回收——**必须明确告知用户**）；
腾空的**空目录单列给用户选**、别顺手删；
流程铁律＝**生成清单 → dry-run → commit → 逐条核对原位置（不是抽样）**。

## D1 诊断（只读，出方案，过闸门G）

### 第 0 步 · 先判断工作区的既有聚合方式

这一步**决定方案走向**，不可跳过：

| 类型 | 特征 | `任务/` 的角色 |
|---|---|---|
| **日期型** | 文件本来就是按时间产生的、彼此独立（报告、测算、会议材料） | **主要归口**：全部按 `任务/YYYY-MM-DD_主题/` 收纳 |
| **领域聚合型** | 工作区已有**更强的聚合轴**——按项目／标的／客户／站点／产品线建好的文件夹 | **只承接「不绑这些领域」的一次性任务**（工作区基建、审计、临时调研） |

> ⚠️ **领域聚合型的既有文件夹一律不动**：① 它是用户明确的既有约定；
> ② 硬改会打断脚本里的相对路径依赖（**静默失效、不报错**）。
> **"统一整齐"的收益远低于断链的风险。**

### 第 1 步 · 识别问题模式

读扫描结果，找这些特征：根层散落文件、同名多版本
（`报告.docx`／`报告(1).docx`／`最终版.docx`）、孤儿文件、超大文件、临时文件。

### 第 2 步 · 判断任务归属

用**创建／修改时间聚类** ＋ **内容依赖**（脚本读哪些数据）判断；
时间相近、内容咬合的归为一个任务，**不要按文件数量硬拆**。

### 第 3 步 · 出整理方案（≤20 行，格式同闸门G 研讨卡）

必须包含三样：**目标目录树** ＋ **每个散落文件的去向** ＋ **待删清单（含分级与判据）**。

### 第 4 步 · 停下等批复

**一个文件都不动。** 用户明示后才进 D2／D3。

## D2 搬移（可逆，一键回滚）

1. **日期型**工作区：每个任务建 `任务/YYYY-MM-DD_主题/` 并移入对应文件。
   **领域聚合型**工作区：只把**不绑领域**的文件归入 `任务/`，绑领域的按**既有轴**归位
   （进对应项目／标的／客户文件夹），**不改既有文件夹名**。
   移动脚本必须**连同其数据目录一起移**，保持相对路径不断。
2. 用脚本搬，每次移动往 `.workbuddy/archive/迁移日志.jsonl` 写一行
   （源路径／目标路径／时间／md5），便于回滚。
3. 重名不覆盖，加 `-1` 后缀。
4. 为每个任务文件夹补 `_说明.md`；内容**只能写到文件证据支持的程度，不臆测任务结论**。
5. 经验库、复用回执及其他机制目录**保持在根层不动**。
6. 完成后展示新目录树与归并依据，并告知用户可用 `rollback` 一键还原。

## 命令速查

| 目的 | 命令 |
|---|---|
| **判型对账（只读）** | `python3 "$T2" report --root .` |
| **隔离区按类型清单** | `python3 "$T2" quarantine-list --root .` → 确认后加 `--commit` |
| **类型清单（可见形态）** | `python3 "$T2" folder-lists --root .` → 确认后加 `--commit`（每个任务／主题文件夹一份 `_类型清单.md`） |
| 扫描（只读） | `python3 "$T" scan --root . [--group-depth N]` |
| 查重复（只读） | `python3 "$T" dup --root .` |
| 搬移 | `python3 "$T" move --root . --map map.json` → 确认后加 `--commit` |
| 隔离 | `python3 "$T" quarantine --root . --list list.txt` → 确认后加 `--commit` |
| 从隔离区还原 | `python3 "$T" restore --root . --batch YYYY-MM-DD --commit` |
| 回滚搬移 | `python3 "$T" rollback --root . --commit` |
| 清超期隔离区 | `python3 "$T" purge --root . --days 30` → 确认后加 `--commit`（⚠ **`--days` 必须 ≥1**） |
| **清指定批次** | `python3 "$T" purge --root . --batch 2026-10-03,2026-10-05` → 确认后加 `--commit`（与 `--days` 互斥；**可复现**） |

### 参数与文件格式

- `--group-depth N`：`scan` 按路径前 N 层输出「目录分组概览」（默认 1，0 关闭）。
- `map.json`：
  ```json
  [{"src":"报告.docx","dst":"任务/2026-09-07_测算/报告.docx"}]
  ```
- `list.txt`：每行一个相对路径。

> **除 `scan`／`dup` 外，所有命令不加 `--commit` 都只预演，绝不改文件。**

### 平台适配点（换平台前先看这一节）

| 机制 | 本机实测 | 迁移时需重新标定 |
|---|---|---|
| shell 的 `rm` | **是坏 shim** ⇒ 一律用 Python `shutil.move`／`os.remove` | 新平台 `rm` 是否可用、是否走回收站 |
| 真删语义 | `purge` 直删，逐文件写删除日志 | 新平台若有系统回收站，可优先利用 |
| 隔离区保留 | 30 天 | 口径自定，无需标定 |

### 环境注意事项

- 含反引号或特殊字符的写入，**先 Write 成 `.py` 再运行**，不要直接拼 shell 命令。
- 批量操作**每批 ≤10 个**，删完校验，**失败即停**。
