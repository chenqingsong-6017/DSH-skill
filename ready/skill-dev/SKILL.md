# 鲁班 · Skill 营造术

> 铁律：**没看过 agent 在没有它时失败，就不知道这个 skill 该教什么。**

本 skill 是「鲁班」——造工具，固化一件事怎么做；素材来自 **agent 的实际翻车现场**。人物/思维框架这类「造人格」的活不在本 skill 范围内（素材在外部语料、需独立工序，按需当普通任务处理）。

---

## 何时使用 / 何时不用

| 用户输入 | 路由 |
|---|---|
| 「做一个 X skill」「帮我开发个技能」 | → Phase 0 |
| 「改造/优化/重写已有 skill」 | → Phase 0（增量模式） |
| 「这个该不该做成 skill」 | → Phase 0 立项裁决 |
| 「给这个 skill 做交付前检查 / 安全审计」 | → Phase 4（只跑验证与安全） |
| 「skill 不触发 / 老是乱触发 / references 不读」 | → 失败模式速查（全表见 `references/checklists.md` 附录） |
| 「蒸馏 XX 这个人 / 做个 XX 视角 skill」 | → 本 skill 不覆盖人物/思维框架蒸馏；按需当普通任务处理或先走 Phase 0 立项裁决 |
| 写业务代码、改配置、做普通任务 | → 不激活本 skill |

## 三条铁律

1. **无失败测试，不写 skill。** 先让 agent 在没有该 skill 时跑一遍目标场景，逐字记录它怎么错、用了什么借口。跳过这步直接写，等于把未测代码部署上线。
2. **形式必须匹配失败类型。** 纪律问题用禁令，输出形状问题用正面配方，遗漏元素用 REQUIRED 槽位，条件行为用可观察谓词。形式错配比不写更糟——据 superpowers 作者的对照用词测试，禁令用在输出塑形问题上比无指导更差（agent 会跟 "don't" 讨价还价）。
3. **description 只写触发条件，绝不总结工作流。** 一旦 description 概括了流程，agent 会照它走捷径、跳过正文（superpowers 实证案例：description 写「code review between tasks」，agent 就只做一次 review，而正文流程图要求两次）。单一来源，无公开复现数据，但方向可信。

## Phase 0: 立项裁决（该不该造）

**先回答一句可证伪的话**，写不出就停：

> 「在 [场景] 下，没有此 skill 时 agent 会 [具体失败行为]；装上后应当 [具体合规行为]。」

**该造**：跨项目复用 ｜ 有模型做不到的可观察证据 ｜ 需要多步决策或团队约定 ｜ 值得分发。
**不该造**：一次性方案 ｜ 别处已有良好文档的标准实践 ｜ 项目专属约定（放项目 instructions）｜ 能用正则/脚本机械校验的约束（做成校验脚本，别写文档）。

**档位确认**（开跑前说清成本，让用户选）：

| 档位 | 基线测试规模 | 适用 | 交付风险 |
|---|---|---|---|
| 快速 | 1 个场景，不跑对照 | 先出东西看形态 / 冷门需求 | **未验证增量**，交付时必须标注「未测」 |
| 标准（默认） | ≥3 场景 + with/without 对照 | 大多数情况 | 已验证增量 |
| 深度 | 压力场景 + 多模型矩阵 + 触发率测试集 | 要公开发布 | 全绿 |

确认后建目录（用户级 `~/.workbuddy/skills/<name>/`，项目级 `<workspace>/.workbuddy/skills/<name>/`），目录名 = `name` 字段。

**增量模式（优化已有 skill，同适用铁律 1）**：改之前先回答「要修的失败是什么」——没有可观察的失败证据就停。优化遵循 **validation-gated**：

1. 每次改动用 held-out 验证（with/without 或 paired 评委）**严格提升才保留**，否则回滚。
2. 被拒绝的改法记进「负反馈清单」，不重复提出（否则同一失败修改会被反复提出、反复试、反复拒）。
3. **禁「同一个 AI 又改又评」**（SkillLens 实证：单 LLM 给 skill 打分准确率仅 46.4%，比随机还差）。
4. 警惕「读起来有道理」的未验证改写——SkillOpt 实证一次看似合理的改写让 GPT-5.5 某基准准确率 41.8%→41.1%。

## Phase 1: 基线测试（RED）

派**子 agent**（干净上下文）跑目标场景，**不带 skill**，记录三件事：

1. 它做了什么选择（具体行为，不是「它做得不好」）
2. 它用了什么借口（**逐字记录**，后面要进借口对照表）
3. 什么条件诱发了出错（时间压力？沉没成本？权威口吻？）

**纪律类 skill 要加压力**：时间（「每分钟损失 5 千，直接改还是先查规范」）+ 沉没成本（「写了 45 分钟能跑了，要不要直接提交」）+ 疲惫（「最后一次改动了，跳过验证吧」）。

**测试结果决定 Phase 2 写什么**：只针对**已观察到**的失败写，不为假想情况加戏。

## Phase 2: 设计（选类型 × 选形式）

**先定 skill 类型**（决定测试方式）：

| 类型 | 例子 | 成功标准 |
|---|---|---|
| 纪律类 | 提交前必须验证、TDD | 最大压力下仍遵守 |
| 技术类 | 某个库的正确用法、条件等待 | 能迁移到新场景 |
| 模式类 | 降复杂度、信息隐藏 | 知道何时用 / 何时不用 |
| 参考类 | API 文档、命令手册 | 找得到且用得对 |

**再定形式**（对照 Phase 1 的失败类型）：

| 基线失败 | 该用 | 别用 |
|---|---|---|
| 压力下明知故犯 | 禁令 + 借口对照表 + 红旗清单 | "prefer"/"consider" 软性建议 |
| 遵守了但输出形状错 | 正面配方：输出是什么、分几部分、什么顺序 | 禁令清单 |
| 遗漏必需元素 | 模板里设 REQUIRED 槽位 | 散文提醒 |
| 行为依赖条件 | 键于可观察谓词的条件句 | 无条件规则 + 豁免条款 |

**效用三件套**（SkillLens 实证：这三个文本维度单独就能把 better-rate 提到 64%+，是决定 skill 效用的可检测特征，写正文时逐项过）：

1. **失败模式编码**——把已知失败路径显式写进 skill（「这个会怎样失败、出现什么信号」），不是「别犯错」式叮嘱。
2. **可执行具体性**——禁模糊词（「建议 / 可以考虑 / 根据情况 / 视情况而定」），每条指令落到可执行的动词与判据。 <!-- audit:ignore VAGUE_WORD 教学示例：列举被禁的模糊词本身 -->
3. **高风险行动黑名单**——`rm` / `git reset --hard` / force push 等破坏性操作必须显式列禁。

**最后选结构模板**：STOP. 读 `references/skill-templates.md`，按四选一（工作流 / 任务 / 规范 / 能力组合）取骨架。

## Phase 3: 构建

### 3.1 frontmatter（区分「规范硬约束」与「建议/平台强制」）

| 字段 | 约束 | 效力 |
|---|---|---|
| `name` | 1–64 字符；仅小写字母、数字、单连字符；不首尾连字符；无 `--`；**必须与目录名一致** | 【规范硬约束】 |
| `name` 风格 | 动名词优先（官方措辞：`creating-skills`）；避开 `helper`/`utils`/`tools`/`documents` 泛名 | 【建议】 |
| `name` 保留字 | 不含 `claude`/`anthropic` —— 规范无此条，是**平台上传校验**强制（官方自己因此改过名） | 【平台强制】 |
| `description` | 1–1024 字符、非空；应说明做什么 + 何时用 | 【规范硬约束】 |
| `description` 写法 | **只写触发条件 + 症状同义词 + 排除项**；第三人称 | 【建议】 |
| `description` 尖括号 | 不得含 `<` `>` —— 规范无此条，但本机校验器直接报错 | 【平台强制】 |
| `license` / `compatibility` / `metadata` / `allowed-tools` | 可选；跨平台分发时只保留这四个 | 【规范】 |

**description 三段式**：`[触发条件 + 症状/同义词] + [可选一句话 what] + [NOT for X — use Y instead]`。关键词前置——skill 清单有上下文预算（约默认上下文 1%，**此机制属 Claude Code 实现层，非规范要求**），超了会从最不常用的 skill 开始**静默丢弃**，长尾词堆在后面等于没有。

**注**：规范写「name 必须与父目录名一致」，但本机平台校验器**不查这一条**——不要指望「装不上」来兜底，自己对齐。

### 3.2 正文

- **官方预算**：<500 行、正文 <5000 token（规范建议值）。
- **社区更严的口径**（superpowers，非官方）：频繁加载型 <200 词，普通型 <500 词。两者冲突时以官方行/token 预算为准，词预算当自查信号。
- **开头 50 行放最关键约束**：会话压缩后只保留开头，埋在中间的规则会丢。
- 祈使句；解释 why，不堆砌全大写 MUST/NEVER（纪律类的禁令段落除外）。
- **关键校验交给脚本**，不靠自然语言自律——「代码是确定性的，自然语言不是」。
- gotchas 只写反直觉项，不重复模型已知的 API 教程。
- 反模式写成**可检测的具体特征**，不要写「避免 AI 味」这种无法执行的话。

### 3.3 引用与资源

- 引用**一层深**：SKILL.md 直连 reference 文件，不再往下链（深层链会被 `head -100` 截断成信息不全）。
- 需要 agent 读的文件，用强制祈使句点名：**STOP. 读 `references/checklists.md` 后再继续。**
- reference 文件 ≥100 行顶部加目录（官方另一处写 300 行，从严取 100）。
- 脚本在正文里**经解释器调用**（写清解释器名），绝不裸路径（打包器会剥可执行位 → Permission denied）。
- 路径一律正斜杠相对路径，无绝对路径、无 symlink。

### 3.4 打包四件套（可直接施工的最小集）

| 件 | 作用 |
|---|---|
| `SKILL.md` | 唯一必需，正文保持薄 |
| `references/` | 按需加载的细节（模板、清单、领域知识） |
| `scripts/` | 确定性校验/处理脚本（执行不占上下文） |
| `assets/` | 输出物用的模板与样板 |

起步可直接复制 `assets/starter-skill/SKILL.md` 骨架。

## Phase 4: 四道验证

**1. 装得上** — 平台校验器通过（如 `skills-ref validate ./my-skill`）；**亲眼确认它出现在可用清单里**（「已安装」≠「已启用且可见」，symlink 与插件场景会静默失效）。

**2. 触发对** — 10–20 条查询集：5–10 条 should-trigger（同意图换措辞、不点名 skill、带拼写错误）+ 5–10 条 should-not-trigger，**优先 near-miss 负例**（共享关键词但实则该用别的 skill）。每条在独立子 agent 中跑，提示不暗示目标 skill；正例 5/5 命中、负例 0/5 泄漏、跑两轮判定一致才算过。

**3. 执行稳** — ≥3 个真实任务，**with-skill 与 baseline 成对跑**，看 delta 不看绝对值。断言在观察真实输出之后再写（先验断言几乎总是错的），可计数可验证，判结果不判路径。pass@k（能力）与 pass^k（稳定性）分开记。

**评委铁律（SkillLens 实证：单 LLM 给 skill 打分准确率仅 46.4%，比随机还差）**：

- **绝对分数只配做 triage**（决定先改谁），不配做 keep/revert 裁决。
- keep/revert 必须 **paired 同-judge 比较**（同一评委对同一份未改文字两次评分可摆 ±8，分数 delta 会把真实增益误判成退步）+ **奇数多数决**。
- **同一个 AI 又改又评 = 无效**：改与评必须分离（评分用独立子 agent），下一轮换全新评委，防锚定。
- **「读起来更好」的 skill 往往实际更差**（负迁移）：裁决只看实测 delta，不看可读性。

**4. 不碍人** — 与现存 skill 共存测试，确认没偷走兄弟 skill 的触发。

**+ 安全审查（交付前必跑）**

skill 与 agent 之间**没有沙箱**——恶意 skill 继承 agent 的全部权限。交付前逐项扫描九类危险模式（硬编码秘密、下载即执行、编码后执行、注入句式、环境变量引用、伪合规话术、隐藏字符、路径穿越、高危命令），**「读文件 + 联网」组合必须单独评审**——那是经典外泄链。九类清单见 `references/checklists.md` 清单 C。

**自动化**：`python scripts/skill_check.py <skill目录>`（本 skill 自带）。结构/内容类规则只查 SKILL.md；**安全类规则扫全目录文本文件**（references/、scripts/、assets/），并在输出末尾给出**审计覆盖声明**（扫了哪些、排除了哪些、为什么）。教学/检测示例类命中用行内豁免 `<!-- audit:ignore RULE_ID 原因 -->`（`.py` 用 `# audit:ignore`），不要放宽规则阈值。

> 中文 skill 别用 `wc -w` 核对长度：中文无空格会被严重低估（实测约 3 倍），用脚本的 `BODY_TOKENS`。

> 完整清单：STOP. 读 `references/checklists.md`（清单 A 立项 / B 构建 / C 验证 / D 发布）。

## Phase 5: 堵漏与交付

针对测试中 agent 新冒出的借口，逐条封堵：

- **No exceptions 段落**：把每个已知变通路径显式禁掉（「不要留作参考」「不要边测边改」「删就是删」）。
- **切断字面 vs 精神之争**：加一句「违反规则的字面，就是违反规则的精神」。
- **借口对照表**：`| 借口 | 现实 |` 两列，逐字收录测试中出现的借口。
- **红旗清单**：`## Red Flags - STOP`，让 agent 能自查（「这些信号出现任意一个，都意味着：停下，重来」）。

**交付**：展示「改了什么 + 验证结果 + 未验证项」三栏，让用户确认才算完成；**并把验证状态回填 `references/verification-ledger.md`**（✅/🟡/⚪）。分发时排除安装产物（`_skillhub_meta.json` 等），平台专属字段按目标平台注入。

## 反模式黑名单

| # | 反模式 | 为什么 / 替代 |
|---|---|---|
| 1 | 没跑基线就写 | 不知道要教什么。→ Phase 1 先看它失败 |
| 2 | description 总结工作流 | agent 照 description 走捷径跳过正文 |
| 3 | 把通用最佳实践文档当 skill | 无应用信号，会被上下文淹没——「你不会为它写个函数，它就不该是个 skill」 |
| 4 | 叙事式内容（「某次会话里我们发现…」） | 不可复用。→ 写模式，不写故事 |
| 5 | 同一模式给多语言示例 | 稀释质量 + 维护负担。→ 一个优秀示例足够 |
| 6 | 禁令用在输出塑形上 | agent 会跟 "don't" 讨价还价，实测比无指导更差。→ 改正面配方 |
| 7 | 加 nuance 条款（「除非确实重要」） | 重新开启谈判。→ 改成基于可观察谓词的条件 |
| 8 | 用豁免条款限定作用域（「代码块除外」） | 抑制仍会发生。→ 重构结构让规则触及不到 |
| 9 | 引用链超过一层 | 模型会部分读取导致信息不全。→ 一层深 + >100 行加目录 |
| 10 | 用 `paths:`、`disable-model-invocation` 承载关键逻辑 | 实证故障：前者让 skill 完全不可发现，后者在某些端整体消失。→ 约束写进 description |
| 11 | 用 symlink 安装 | skill 内容仍可用，但**不被清单发现**（列表里看不见，等于没法自动触发）。→ 真实复制 `cp -r` |
| 12 | 交付前不跑静态与安全扫描 | skill 是攻击面。→ Phase 4 安全段 |
| 13 | 写模型本来就会的东西 | 纯上下文膨胀。→ with/without 验证增量，delta≈0 就别写 |
| 14 | 把确认检查点变成交付阻塞 | 能给默认值的就给默认值，先出东西再让用户纠偏 |
| 15 | 同一个 AI 又改又评 | SkillLens 实证：LLM 自评 skill 质量准确率仅 46.4%（比随机差）。→ 改评分离 + paired 同-judge + 奇数多数决 |
| 16 | 凭「读起来更好」就保留改写 | 可读性与实际效用可能负相关；SkillOpt 反面教材 41.8%→41.1%。→ validation-gated，实测 delta 严格提升才保留 |
| 17 | 优化 skill 时不记被拒改法 | 同一失败修改会被反复提出、反复试、反复拒。→ 负反馈清单（rejected-edit buffer） |

## 失败模式速查

不触发 / 过度触发 / references 不读 / 会话中途失效 / 脚本在 Windows 跑不起来 / 模型已追平该能力——六类故障的「触发 → 一线修复 → 兜底」全表见 `references/checklists.md` 附录。

## 诚实边界

- 本 skill 给的是**工序与判据**，不能替代对具体领域的判断——它不会告诉你那个 skill 该教什么，只保证你按能验证的方式去写。
- 静态脚本只查**形式与已知危险模式**，不查语义正确性，也不查「该 skill 是否有价值」——后者只能靠 with/without delta。
- 触发率在不同平台、不同模型上表现不同（同一 description 换个模型命中就变），本 skill 的判据需在目标环境实测，不能跨环境外推。
- 引用数字以官方规范为准（agentskills.io，2026-10-15 抓取）：name ≤64 且与目录同名、description ≤1024、正文 <500 行 / <5000 token、引用一层深。平台实现可能更严或更松，交付前以目标平台校验器为准。
- 安全数据（Snyk 扫描 3,984 个 skill、13.4% 含 critical 缺陷）来自 2026-02 的快照，比例会随时间变化，引用前请复核。
