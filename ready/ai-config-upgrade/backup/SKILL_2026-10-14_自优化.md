# AI 配置升级流程（调研式）

把"去 GitHub 调研大佬做法 → 对照现状 → 融合优化"固化为标准七步流程。
源自 2026-10-11 实战三连（自定义指令 v3／SOUL.md v3.0／记忆体系 v1.1），已经用户验收；v2（2026-10-13）按本流程自升级，补齐结构四段。

## 适用范围

优化以下任一配置项（可扩展）：
- **自定义指令**（WorkBuddy：设置 →「功能」→ 个性化 → 自定义指令）
- **人设设定**（`SOUL.md`）
- **长期记忆**（`MEMORY.md` / `MEMORY-GUIDE.md` / `memory-bank/`）
- **工作区规则**（如 TraeCode 固定规则、任务提示词）

触发信号："优化/升级 XX""去 GitHub 看大佬的""按最佳实践改 XX"。

## 不适用范围（何时不用）

| 场景 | 该用什么 |
|---|---|
| 从零创建新配置／新 skill | `skill-creator` |
| 只查第三方项目/包的实证数据（星数、活跃度、许可证） | `github-empirical-research`（本 skill 第 2 步可调用它） |
| 纯知识点问答 | 直接答 |

## 三条硬规则（违反即返工）

1. **备份先行 + 零删除融合**：改前备份到 `backup/`；保留用户既有内容，融合而非替换（用户原话："结合优化"）；「删改」只允许下沉，不允许删除。
2. **调研必须落到可照抄的共识清单**：3~6 条、每条可操作、注明来源；泛泛而谈的调研不算完成。
3. **界面缓存提醒必做**：云端/客户端配置交付粘贴版后，必须提醒「关闭旧面板重开，勿在旧缓存上点『编辑』保存」（会覆盖修改）。

## 七步流程

### 第 1 步 · 定位对象（先确认"改哪一层、能不能直改"）

判定配置的存储形态，分三态：

1. **本地文件可直改** → 直接改文件（如 SOUL.md、MEMORY.md、规则文件）。
2. **云端/客户端配置** → 本地无明文。排查顺序：`settings.json` → `workbuddy.db`（SQLite，只读查询）→ `storage/` → `local_storage/` → 全域 grep。确认不可直改后，**产出"可粘贴文本 + 3 步操作路径"**，由用户在界面粘贴。
3. **混合** → 文件部分直改；界面部分给粘贴版。

已知对应关系（WorkBuddy，实测）：
- 「人设设定」面板 ↔ `~/.workbuddy/user-*-personal/SOUL.md`（**可直改文件**）
- 「长期记忆」面板 ↔ 同目录 `MEMORY.md`（**可直改文件**）
- 「自定义指令」 ↔ 账号级配置（**不可直改，走粘贴版**）

### 第 2 步 · GitHub 调研（至少 3 路并行搜索）

- 英文线：主题 + "best practices / GitHub / template"
- 中文线：主题 + "最佳实践 / 大佬 / 模板"
- 生态线：相关标准概念关键词（如 SOUL.md / MEMORY.md / system prompt / agent memory）
- 从结果中挑 2~3 个高价值来源 WebFetch 取细节（官方文档、高星仓库、模板原文——优先拿"可照抄"的原文）
- 产出**共识清单**：3~6 条，每条可操作、注明来源

### 第 3 步 · 侦察现状

- 完整读取当前配置
- 核对硬指标：字符数上限（如记忆类文件注入上限 4000）、体量区间（如 SOUL.md 30–80 行共识）
- 用 `scripts/check_chars.py` 复核尺寸（用法见脚本内注释）

### 第 4 步 · 差距分析

- 逐条对照"共识 vs 现状"：缺什么／哪里违反最佳实践／哪里臃肿
- 分两类：**补短板**（新增缺项）与**做减法**（压缩／下沉／去重）
- 顺序：先补短板，后做减法

### 第 5 步 · 实施（三条铁律）

1. **备份先行**：改前备份到 `backup/`，命名 `X_日期_缘由.md`。
2. **零删除融合**：保留用户既有内容，融合而非替换（用户原话："结合优化"）。多版本迭代时提供"旧版存档 + 回退路径"。
3. **大条目下沉**：核心文件只留"结论 + 指针"，细节迁入详情层（memory-bank 等），并同步更新索引。
- 每次写入后**复核**（字符数／完整性／格式）。
- 交付前做一次「前后条款打架」检查（如"简单问题直接答"须写成质量考量，否则与"质量优先"条款冲突——见 cases.md 案例 1）。

### 第 6 步 · 交付说明（落盘）

- 命名：`X优化_Y_v版本_日期.md`
- 结构：① 共识摘要（含来源）② 差距分析表 ③ 改动清单（含前后数字）④ 生效方式 ⑤ 风险
- **生效方式必含界面提醒**：设置面板若开着旧内容须"关闭重开"；**不要在旧缓存上点「编辑」保存**（会覆盖修改）

### 第 7 步 · 收尾

- 风险自查 ≥2 个（含"怎么验证生效"）
- 记忆落盘：写工作区日志；涉及全局配置的同步更新对应记忆文件
- 交代可回退路径

## 反模式（交付前自检）

- ✗ 没定位存储层就动手——改错位置＝白改（SOUL.md 案例：根目录另有一套旧模板，真正生效的是 personal 目录那套）。
- ✗ 调研产出泛泛而谈（无来源、不可照抄）。
- ✗ 替换式重写，违反"结合优化"。
- ✗ 下沉后不更新索引——用时找不到。
- ✗ 忘界面缓存提醒——改动被旧缓存覆盖。
- ✗ 交付前没做条款打架检查。

## 输出规范

- 全程中文；英文术语当场给中文
- 交付文档用第二人称（用户可直接转发）
- 每次改动留痕：版本号 + 日期 + 备份路径
